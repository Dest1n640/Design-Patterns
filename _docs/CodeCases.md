## Требования к исходному коду
Редакция: **2026-09-27**

### Основные положения

- По возможности пишите самодокументируемый код [link](https://habr.com/ru/post/458264/)
- При именовании объектов придерживайтесь английского языка и подбора корректных доменных терминов
- При проектировании классов придерживайтесь принципов SOLID (https://en.wikipedia.org/wiki/SOLID), а также по возможности классическими принципами `KISS`, `DRY` и `YAGNI`
- При проектировании архитектуры решения придерживайтесь принципов чистой архитектуры (https://github.com/jasontaylordev/CleanArchitecture)

### Форматирование кода Python

- Наименование каталогов должно соответствовать [`CamelCase`](https://ru.wikipedia.org/wiki/%D0%92%D0%B5%D1%80%D0%B1%D0%BB%D1%8E%D0%B6%D0%B8%D0%B9_%D1%80%D0%B5%D0%B3%D0%B8%D1%81%D1%82%D1%80): `Src`, `Core`, `Models`, `Tests`
- Наименование классов должно соответствовать [`PascalCase`](https://ru.wikipedia.org/wiki/CamelCase) (`OrganizationModel`, `NamedModel`), в соответствии со стандартом [PEP 8](https://peps.python.org/pep-0008/#class-names)
- Наименование свойств, методов, функций и переменных должно соответствовать `lowercase_separated_by_underscores`
- Классы-исключения сохраняют суффикс `Exception` (`ApplicationException`, `ValidationException`)
- Доменные модели в каталоге `Models` сохраняют суффикс `Model` (`OrganizationModel`, `WarehouseModel`); базовая иерархия в `Core` строится на той же основе, без слова "Entity": `AbstractModel` → `NamedModel` → конкретные `*Model` в `Models`

- **Обязательно** наличие docstring для каждого класса, метода и свойства:
  - одна строка на русском языке, с заглавной буквы, с точкой в конце
  - без обязательных секций `:param:` / `:raises:` — сигнатура и type hints уже показывают, что за параметры; секции добавляйте только если поведение метода неочевидно из названия и сигнатуры

```python
class OrganizationModel(NamedModel):
    """Класс сущности - организация."""

    @property
    def inn(self) -> str:
        """Возвращает ИНН организации."""

    def _validate_inn(self, value: str) -> None:
        """Проверяет, что ИНН — строка ровно из 10 цифр."""
```

Даже устоявшиеся акронимы (`ИНН`, `БИК`) в именах свойств/методов/параметров пишем строчными буквами (`inn`, `bic`) — так требует `PEP 8` и правило `N` (pep8-naming); заглавные буквы в тексте документации/сообщений об ошибках это не затрагивает.

### Статический анализ

- Проект использует [`ruff`](https://docs.astral.sh/ruff/) как единственный линтер и форматтер
- Конфигурация — в `pyproject.toml` (`[tool.ruff]`), включённые наборы правил: `E`, `F` (pyflakes/pycodestyle), `N` (pep8-naming — ловит нарушение регистра классов), `I` (isort — порядок импортов), `UP` (pyupgrade), `B` (flake8-bugbear)
- **Обязательно** перед коммитом/PR прогонять и `ruff check .`, и `ruff format --check .` — оба должны завершаться без ошибок:
  ```sh
  uv run ruff check .
  uv run ruff format --check .
  ```
- Оба шага прогоняются в GitHub Actions (`.github/workflows/ci.yml`) на каждый push и pull request в `main`; ветка `main` защищена правилом, требующим прохождения этой проверки перед мерджем
- Для локальной разработки (необязательно, но рекомендуется) можно сразу поправить то, что чинится автоматически, перед тем как гонять обязательную проверку выше:
  ```sh
  uv run ruff check --fix .
  uv run ruff format .
  ```
  `--fix`/`format` без `--check` **меняют файлы на диске** (например, порядок импортов) — это удобно локально, но не заменяет обязательную проверку выше и не используется в CI, которая должна только проверять, а не молча менять код

### Тестирование

При написании тестов четко разделяйте их по типам: `юнит-тесты`, `интеграционные тесты`, `функциональные тесты / e2e`.
Используйте TDD или отладку с помощью юнит-тестов только для тех блоков, которым не свойственно частое изменение или модификация.
Перед написанием тестов руководствуйтесь здравым смыслом и не забывайте, что тесты - это тоже код, который требует поддержки и актуализации.

- Используем рекомендации [Microsoft](https://learn.microsoft.com/ru-ru/dotnet/core/testing/unit-testing-best-practices), адаптированные под pytest
- Именуем тесты по паттерну **`test_<единица>__<сценарий>__<ожидаемый_результат>`** — двойное подчёркивание разделяет три смысловые части, одинарное используется внутри каждой части:
  ```python
  def test_organization_model__invalid_inn__raises_validation_exception():
      """Создание организации с невалидным ИНН бросает ValidationException."""


  def test_organization_model__valid_fields__all_fields_are_set():
      """Валидное создание организации сохраняет все переданные поля."""
  ```
- **Обязательно** наличие обычного docstring (не "XML-комментария" — в Python такого нет) с кратким описанием сценария для каждого теста
